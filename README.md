# Public HTTPS A2A Invoice Agent

FastAPI + PostgreSQL implementation of the supplied A2A 1.0 invoice-action contract. It proposes evidence-backed actions, waits for grader results, and writes receipt executions only for accepted proposals. It does not initiate real bank payments.

## Files

- `main.py` — A2A routes, validation, OpenAI-compatible model call, task lifecycle, idempotency, per-principal task ownership, semantic decision cache.
- `render.yaml` — Render web service + PostgreSQL blueprint.
- `requirements.txt`, `Procfile` — build/runtime configuration.
- `.env.example` — configuration template; never commit real tokens or API keys.

## Deploy to Render

1. Create a GitHub repository and push these files. Do not commit `.env` or secrets.
2. In Render, choose **New → Blueprint** and connect the repository. Review the web service and PostgreSQL database before creating them. If the free PostgreSQL plan is unavailable for your account/region, select a paid database; durable PostgreSQL is required for reliable persistence.
3. Set `A2A_BASE_URL` to the exact public service base URL, including the trailing `/a2a/`, for example `https://YOUR-SERVICE.onrender.com/a2a/`.
4. Set `A2A_BEARER_TOKENS` to one or more long random bearer tokens separated by commas. Each accepted token is treated as a separate user. The grader must use one of the configured tokens. Do not use `A2A_ALLOW_ANY_TOKEN=true` in production.
5. Set `LLM_API_KEY` from your selected OpenAI-compatible provider. The default is Groq's API endpoint and model; provider availability, free tiers, and model names can change. You can use any compatible provider by setting `LLM_BASE_URL` and `LLM_MODEL`.
6. Deploy and wait for `/healthz` to return `{"ok":true,"database":"ok"}`. Copy the base URL into the challenge page exactly as `https://YOUR-SERVICE.onrender.com/a2a/`.

Render may sleep free web services and free database availability/retention can change. Confirm the current plan limits in Render before relying on it for a graded run. A paid persistent database is safer where free database expiry is a risk.

## Environment variables

| Variable | Required | Purpose |
|---|---|---|
| `A2A_BASE_URL` | Yes | Exact externally submitted base URL, e.g. `https://host.onrender.com/a2a/` |
| `A2A_BEARER_TOKENS` | Yes | Comma-separated token allowlist; each token has isolated task ownership |
| `DATABASE_URL` | Yes in production | Render PostgreSQL connection string; `render.yaml` wires it in |
| `LLM_API_KEY` | Yes | Provider API key |
| `LLM_BASE_URL` | No | Defaults to `https://api.groq.com/openai/v1` |
| `LLM_MODEL` | No | Defaults to `llama-3.3-70b-versatile` |

## Routes

- `GET /.well-known/agent-card.json` — public Agent Card
- `POST /a2a/message:send` — initial invoice batch or result continuation
- `GET /a2a/tasks/{id}` — owner-only task read
- `GET /a2a/tasks` — owner-only task list
- `POST /a2a/tasks/{id}:cancel` — owner-only cancellation
- `GET /healthz` — database health check

All `/a2a` routes require `Authorization: Bearer <configured-token>` and `A2A-Version: 1.0`. POST routes require `Content-Type: application/a2a+json`. A task-specific missing/foreign task responds with a generic 404.

## Local run

Python 3.11+ recommended.

```bash
python -m venv .venv
# Windows PowerShell: .venv\Scripts\Activate.ps1
# macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # PowerShell: Copy-Item .env.example .env
# Set the variables in your shell; do not commit .env.
uvicorn main:app --reload --port 8000
```

For local testing, set `DATABASE_URL=sqlite:///./invoice_agent.db` and use a local PostgreSQL URL for realistic locking tests. `A2A_ALLOW_ANY_TOKEN=true` is only a local convenience if no token allowlist is configured.

## Protocol smoke tests

Replace URL and token first:

```bash
BASE='https://YOUR-SERVICE.onrender.com/a2a/'
TOKEN='YOUR_CONFIGURED_TOKEN'
curl -i "$BASE"../.well-known/agent-card.json
curl -i -H "Authorization: Bearer $TOKEN" -H 'A2A-Version: 1.0' "$BASE"tasks
curl -i "$BASE"../healthz
```

For POSTs, use `Content-Type: application/a2a+json`, `A2A-Version: 1.0`, and `Authorization: Bearer ...`. The message's `parts` must contain the exact custom media type and its `data` object. On an initial batch, expect `task.status.state == "TASK_STATE_INPUT_REQUIRED"` and one proposal artifact. Send the grader's result continuation with the same task/context/batch IDs. Expect `TASK_STATE_COMPLETED` and one receipt artifact; `executions` contains only `ACCEPTED` results.

## Correctness and safety notes

- A proposal is not permission to act. This service never sends money or calls a payment rail; it records accepted action receipts only.
- Every accepted execution is copied from the stored proposal and its matching grader result. Receipt nonces are not generated by the agent.
- Terminal tasks reject later cancellation/result mutations. PostgreSQL `SELECT ... FOR UPDATE` serializes cancel/result races.
- The idempotency hash covers recursively sorted compact JSON of `message` only, not `configuration`; message-ID reuse with changed message content returns 409.
- The decision cache keys by canonical full package content, independent of batch/task/message IDs. New action IDs are generated for each task.
- Tokens are stored only as SHA-256 principal identifiers, not as raw bearer tokens.
- The model output is schema-validated. Ambiguous or malformed model output fails closed rather than producing actions.

## Before submitting

1. Confirm the public URL is HTTPS and the base path is exactly `/a2a/`.
2. Confirm the card's `supportedInterfaces[0].url` matches `A2A_BASE_URL` exactly.
3. Verify your configured token is the token used by the grader.
4. Check that provider key and PostgreSQL URL are set in Render, not in source control.
5. Run the challenge's Check once, inspect its feedback, fix issues, and preserve one check for Save.

This is a starter implementation of the stated contract, not a formal certification of every A2A 1.0 interoperability detail. Run the exact grader probes after deployment; protocol edge cases and provider-specific JSON behavior may require adjustments.
